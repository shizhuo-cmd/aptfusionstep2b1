# 根下分支共享对象二次切分实验记录（2026-08-04）

## 目的

在原有的任务图切分完成后，进一步检查同一根节点下的直接子进程分支是否真的在协作。若两个分支的任意进程访问过同一个原始对象 UUID，则把它们保留在同一任务图；没有共享对象关系的分支则拆开，但每张新图都保留原根节点。

本实验只运行模块 1 和模块 2，没有运行模块 0。模块 2 固定使用同一套 normal-only 检测配置，因而结果差异只来自二次切分。

## 实现

1. 从 `Event.subject`、`predicateObject` 和 `predicateObject2` 提取原始 UUID，并先按照现有规则完成线程到进程的归并。
2. 只接受日志中实际出现的 FileObject 和 NetFlowObject UUID；不使用路径、对象类别名或后续归一化的 `object_key`，避免把不同原始实体误并。
3. 只保留至少被两个不同规范进程访问过的对象。独占对象不可能连接两个分支，因此这一过滤不改变规则语义。
4. 对每个待处理任务图，为根的每个直接子树赋予一个分支编号。使用 `object UUID -> 首次看到它的分支` 的倒排索引；同一对象在另一分支出现时，用并查集合并两个分支。
5. 并查集的每个连通分量输出一张新图，且保留原根节点与原有边界节点。

该方法按进程-对象关联扫描，避免了“每个分支与其他所有分支逐节点、逐事件比较”的平方复杂度。

## 两次尝试

首次实现把每个进程关联的全部对象 UUID 都交给组件层扫描。CADETS 在节点表示生成后长时间无输出，属于性能失败；对应部分产物保留为：

`artifacts_cadets_normal_only_branch_object_overlap_branch_object_overlap_20260804_failed_unbounded_object_cardinality`

随后改成上述“仅跨规范进程共享对象”索引后，CADETS 与 TRACE 均能完成。TRACE 的结果出现明显指标回退，因此产物明确标记为：

`artifacts_trace_normal_only_branch_object_overlap_branch_object_overlap_20260804_failed_metric_regression`

## 结果

### 切分统计

- CADETS：5,247 个输入组件中有 1,262 个被拆分，输出 6,896 个组件。大图数量没有实质下降，节点数大于 500 和大于 1,000 的图均仍为 15 个；但漏检从 2 张降到 1 张。
- TRACE：1,108 个输入组件中有 489 个被拆分，输出 10,922 个组件。许多组件被拆成几十张小图，导致中位规模从 11 降到 2，正常任务的碎片显著增多，最终引入 45 张误报。

## 结论

1. 共享对象二次切分不是通用默认规则。TRACE 的任务图原本规模适中，该规则会把正常进程树拆得过碎，模块 2 的阈值和正常原型不再稳定。
2. CADETS 的正类大根任务图中存在一部分与其他分支没有对象协作的内容；本次拆分使任务图检测召回率提高，并带来小幅宏 F1 增益。但最大大根图几乎未缩小，说明其主要子分支之间仍由共享对象连通，不能仅靠这一规则分开。
3. 后续若继续推进，应只把该逻辑作为 CADETS 的受控候选，并增加触发门槛，例如只处理 synthetic root、超大图或具有可疑执行锚点的根，而不应用于 TRACE 的所有任务图。
